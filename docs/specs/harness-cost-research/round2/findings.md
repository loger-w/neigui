## 五條可執行建議

### R1. 先看 model,再看別的(唯一數量級等級的槓桿)

同一個檢索題,三個 model 答案都正確:

| model | 成本 | 相對 |
|---|---:|---:|
| claude-fable-5 | $0.6870 | 4.74× |
| claude-opus-5 | $0.1449 | 1.00× |
| claude-sonnet-5 | $0.2165 | 1.49× |

差距只有一半來自牌價(fable $10/$50 vs opus-5 $5/$25),另一半來自 fable 在同一題上多用了
26% 的 prompt。而語料裡 **$3,991(76.6%)花在 fable-5**。

**注意 sonnet-5 的反直覺結果**:牌價最便宜($2/$10 intro),總成本卻比 opus-5 高 49%,
因為它探索了 2.1× 的 context。**「換小 model 省錢」不成立,要看總成本不是牌價。**

這條要不要動是 user 的判斷(fable 的能力是不是值那 4.74×),本輪只負責把數字放上桌。

### R2. 同一個 phase 要讀的檔,一次 message 發完所有 Read

實測拆 turn 的代價:prompt **3.08×**、成本 **+29%**,內容一模一樣。

Round 1 的 R4 建議「把 Phase 0 的三支 ref 合併成一支檔案」,省 284 token。**同一件事有個
零檔案改動的做法**:在流程檔寫明「本 phase 的 refs 用單一 message 的平行 Read 一次讀完」。
省的是 turn(乘數),不是 bytes(加數),而且不必動任何檔案結構。

### R3. 流程檔明確標 effort,預設 `medium`

`xhigh` → `medium` 在同一題上省 **52%**。這是流程層可以直接設的旋鈕,目前沒設。

保留一句注意:實測 `low` 比 `medium` **貴 18%**(n=2,未定論)——推測 low 少想一步、
多繞幾次工具把省下的又賠回去。**所以是往 `medium` 收斂,不是一路往 `low` 壓。**

### R4. 停止在常駐層瘦身上投入(附價目表供死心)

| 節 | Δ tokens | 語料尺度可省 |
|---|---:|---:|
| §1 啟動 & 驗證 | −999 | $11.6 |
| §3 React / TS 風格 | −988 | $11.5 |
| §4 跨檔契約 | −934 | $10.9 |
| §7 版本管理慣例 | −738 | $8.6 |
| §8 主題 skills 索引 | −691 | $8.0 |
| §2 Python 風格 | −616 | $7.2 |
| §6 / §5 / §0 / 序言 | −825 | $9.6 |
| **整份** | **−5,774** | **$67(1.0%)** |

三個理由:

1. 常駐層只佔每 turn prompt 的 **24.1%**(turn 1 是 55,828 tok,session 平均每 turn 是
   244,892 tok)。其餘 76% 是 session 自己累積的對話與檔案。
2. 常駐層裡最大的一塊是**內建 tool schema(57.8%)**,而它動不了。CLAUDE.md 只佔 14.3%。
3. 逐節加總與整份全刪只差 0.3%,所以這張表就是全部 —— 沒有藏起來的大魚。

**要刪 CLAUDE.md 的內容,理由應該是「注意力」或「這條已經過期」,不要再用「省錢」當理由。**

### R5. 撤回 round 1 的 R1(集中改 harness 檔)

Round 1 寫「這條不需要動任何檔案,效益卻高於本輪所有結構改動的總和」。實測:

- 失效是**局部**的:40k 的 prefix 只有後段 14-19k 重寫,前 26k(system prompt + tool schema)不動。
- 失效是**一次性**的:改回去立刻恢復全命中(乾淨/髒兩個狀態各有 entry,同時存活)。
- 失效按**狀態**計價不按次數計價:配對複製顯示同一個 git 狀態第二次出現就全命中。
- 換算:一次 ~18k write 在 fable 費率 = **$0.37**,對中位 $97.93 的 `/auto` session 是 **0.4%**。

**這條該從操作規則裡拿掉**,它不值得任何作業節奏上的犧牲。

## 順帶查到、值得單獨處理的兩件事

1. **`/refactor` 在 303 個 session 裡一次都沒被叫用過。** 它仍在被維護(round 1 的改版動過它,
   它也吃著 skill 清單的常駐配額)。要嘛承認它沒需求、退役掉,要嘛找出為什麼想 refactor 時
   不會想到它。
2. **`/feat` 中位單次 $191.83、344 個 turn**,是最貴的流程,且 61.2% 的 turn 花在 subagent。
   R1-R3 三條建議套用在 `/feat` 上的回報最高。

## SC 指標該怎麼改(接 round 1 R3)

Round 1 提議「峰值 × turn 數」。本輪資料支持這個方向,但要修一項:

```
session 成本 ≈ Σ_over_turns( 常駐層 + 該 turn 已累積的 context ) × 費率
             ≈ turn 數 × 平均 context × 費率
```

實測係數:常駐層佔平均 context 的 **24.1%**,累積佔 **75.9%**。所以「載入量」這個 SC 指標
最多只能碰到 1/4 的成本,而且是加數;**turn 數與 model 是乘數**。

**建議:SC 別再量 bytes 或載入量,改量「該流程的 turn 數」與「跑在哪個 model」。**
兩者都能從 transcript 直接取得(`corpus3_flows.py` 已經在做),不需要新的量測基建。

## 方法論:這輪學到最重要的一條

**探針的形狀決定結論的形狀。**

Round 1 用「回 OK」的單次 API call 探針量了 45 個實驗。在那種 session 裡,開場 prompt 就是
全部成本,所以任何影響開場 prompt 的東西看起來都極重要。真實 `/feat` 有 344 個 turn,開場
只佔 1/344 的權重。**同一批數字,換一個分母,排名整個翻過來。**

兩次靠陽性對照擋下錯誤結論:A3 的「什麼都不改也失效」揭穿了 n=1 歸因不可信;A4 的配對複製
在第 1 輪完美支持假說之後,第 2、3 輪把它推翻 —— 只跑一輪就會發表一條反過來的操作規則。
