## 這一輪為什麼要有

Round 1 的 45 個實驗全部是 **synthetic probe**:`claude -p` 打一個「回 OK」的提示,量它的
prompt 大小。那量到的是「一個 session 開場要付多少」,而不是「跑完一次 /feat 要付多少」。

Round 2 加了一個 round 1 沒有的資料源:**331 個真實 session 的 transcript**
(`~/.claude/projects/**/*.jsonl`)。每則 assistant 訊息都帶完整 usage(input /
cache_creation 分 1h、5m / cache_read / output / model / effort / sidechain),可以直接
還原每一塊錢花在哪。結果是 round 1 的槓桿排名**前兩名都站不住**。

### 量測方法

| 項目 | 觀測批 | 實驗批 |
|---|---|---|
| 來源 | 真實 session transcript | `claude -p --output-format json` |
| 指標 | 依官方 multiplier 還原的美元 | `write` / `read` **分開**,不取和 |
| 為何分開 | — | 這輪的題目多半是「快取狀態」,而和在命中與否之間是守恆的,看不出差別 |
| 定價 | fable $10/$50、opus $5/$25、sonnet $2/$10(intro)、haiku $1/$5;write 5m=1.25x、1h=2x、read=0.1x | 同左 |

## 假說與結果

### H16 — headless session 的 prompt cache 幾分鐘就過期

**預測**:預設 5 分鐘 TTL,所以跨 phase 有等待的長流程會反覆掉出快取(round 1 未解問題之一)。
**實驗**:E61-E63(寫入後隔 1s / 90s / 400s 再打同一 prefix)。
**結果:推翻。**

| 間隔 | write | read |
|---|---:|---:|
| ~1s | 0 | 40,276 |
| 90s | 0 | 40,270 |
| 400s(>5min) | 0 | 40,276 |

三次全部**完全命中**。實測 TTL ≥ 6.7 分鐘,與語料裡「1h TTL 佔 write 的 38.5%」一致 —— 這條
管道用的是 1 小時 TTL,不是預設的 5 分鐘。**「長流程會掉出快取」這個擔憂不成立,不必為它做設計。**

### H17 — 改任何一個進 prompt 的檔,下一個 session 就付全額 write

**預測**:成立(round 1 R1 的操作規則就建立在這上面)。
**實驗**:E64-E70(對照 / 改 CLAUDE.md / 改 code / 加 untracked 檔,各自再測還原後)。
**結果:部分成立,而且被 round 1 嚴重高估。**

| 條件 | write | read | 判讀 |
|---|---:|---:|---|
| 對照:什麼都不改 | 0 | 40,270 | 基準是熱的 |
| 改 CLAUDE.md 內容 | 14,293 | 25,983 | **只失效 14k / 40k** |
| 把 CLAUDE.md 改回來 | 0 | 40,276 | **舊 entry 還在,立刻恢復全命中** |
| 改 backend code | 18,709 | 21,569 | 不進 prompt 的檔也會失效 |
| 加 untracked 檔(深層目錄) | 0 | 40,276 | 反常 → 交由 H25 追 |

兩個 round 1 沒看到的性質:

1. **失效是局部的。** prefix 前約 26k(system prompt + tool schema)不受影響,只有後段
   約 14-19k 要重寫。Round 1 的「9.5×」是拿**整個 session 只有一次 API call** 的探針算的,
   那種 session 裡 write 就是全部成本。
2. **還原就恢復。** 改回去之後立刻全命中,代表舊的 cache entry 一直在。變更的代價是**一次性**的,
   不是持續的。

**換算到真實工作量**:一次 18,709 tok 的 write,在 fable 費率(1h write = $10/M × 2)是
**$0.37**。對一個中位 $97.93 的 `/auto` session 是 **0.4%**。

> **這條推翻了 round 1 的 R1。** Round 1 說「集中改 harness 檔…效益高於本輪所有結構改動的
> 總和」,那是把一個單次 API call 探針的比值,當成真實 session 的比值。實際是 0.4%。

### H19 — 常駐層最大的一塊是 CLAUDE.md

**預測**:成立(round 1 H3 的結論)。
**實驗**:E85-E88(關掉一整類常駐內容)。
**結果:推翻。最大的是內建 tool schema,是 CLAUDE.md 的 4 倍。**

| 條件 | prompt | Δ | 佔 baseline |
|---|---:|---:|---:|
| baseline | 40,295 | — | — |
| `--tools ""`(關掉所有內建工具 schema) | 17,008 | **−23,287** | **−57.8%** |

| `--disable-slash-commands`(關掉 skill 清單) | 37,493 | −2,802 | −7.0% |

### H22 — 委派 subagent 比 coordinator 自己做便宜

**預測**:成立(觀測批 O3:subagent 佔 55% turn 但只佔 20.6% 成本)。
**實驗**:E95 / E96(同一題,opus,自己做 vs 用 Task tool 派一個 subagent)。
**結果:推翻(對小任務)。**

| 條件 | prompt | output | cost |
|---|---:|---:|---:|
| opus 自己做 | 138,023 | 416 | $0.2163 |
| opus 委派 subagent | 87,411 | 266 | **$0.4669** |

委派讓 **coordinator 自己的 prompt 少了 37%**,但**總成本變成 2.16×** —— subagent 要自己
付一份常駐層,coordinator 還要再讀一次它的回報。

**O3 與這條並不矛盾**:subagent 的**每 turn** 成本確實低(它的 context 小),但把一個
coordinator 三兩下能做完的事丟給 subagent,是淨增加成本。委派的收益來自**平行**與
**context 隔離**,不是省錢。

### H25 — 到底什麼會讓下一個 session 掉出快取

**由 H17 的反常引出**:E67(改一個不進 prompt 的 tracked 檔)失效,E69(加一個 untracked 檔)
不失效 —— 兩者都動了 `git status`,結果卻相反。
**實驗**:E102-E126(A2 歸因 → A3 複製 → A4 配對複製),共 25 個。

**第一層(A2)——反常解掉了**:E69 那個 untracked 檔建在
`docs/specs/harness-cost-research/round2/` 底下,而那個目錄**本身就已經是 untracked**,
所以 `git status --short` 的輸出**逐位元組沒變**。把 untracked 檔改建在 repo 根目錄(E107),
就失效了 18,718 tok。→ 失效源是 **system prompt 裡的 gitStatus 段**。

**第二層(A3)——對照失敗,擋下錯誤結論**:三次「什麼都不改」的對照裡有一次(E110)也寫了
14,293 tok。基準本身會漂,單次量測分不出「我造成的失效」與「它自己漂」。同一批的
E113-E115(建立被 gitignore 的檔,三複製)全部 `write=0` → **gitignore 的檔不會失效**;
E109(重寫 tracked 檔但內容逐位元組相同)也 `write=0` → **只動 mtime 不會失效**。

**第三層(A4)——配對複製推翻了因果的簡化版**:

| 輪次 | 對照 write | 處置(改 tracked 檔)write |
|---|---:|---:|
| 1 | 0 | **18,724** |
| 2 | 0 | **0** |
| 3 | 0 | **0** |

三輪的處置 prompt 都是 40,303(相同),對照都是 40,289/40,295。也就是說:

> **失效不是「每改一次付一次」,而是「每一個沒見過的 prefix 狀態付一次」。**
> 改 tracked 檔把 git status 從 `clean` 變成 `M backend/main.py`,那是一個**新狀態** →
> 第一次付 write;之後只要回到同一個狀態(不管是第 2 次改、還是改回去),都是全命中。
> 乾淨狀態與髒狀態**各自有自己的 cache entry,而且同時存活**(E120/E123/E126 全命中)。

**這條把 round 1 的 R1 從「最高 CP 值建議」降級成「幾乎不用管」**:一個 build loop
一天之內只會在有限幾種 git 狀態之間循環,而每種狀態一小時內只付一次 ~$0.37。

## 方法論教訓

### 探針的形狀決定結論的形狀

Round 1 的 45 個實驗全用「回 OK」的單次 API call 探針。那種 session 裡,**開場 prompt 就是
全部成本**,所以任何影響開場 prompt 的東西都會顯得極重要。真實的 `/feat` 有 344 個 turn,
開場只佔 1/344 的權重。同一組數字,換一個分母,排名整個翻過來。

**可帶走的規則:量成本效率時,探針的 turn 數必須與被優化的對象同一個量級,否則量到的是別的東西。**

### 陽性對照兩次擋下錯誤結論

1. **A3 的 E110**:「什麼都不改」的對照也失效了。若沒做這個對照,A2 那批 n=1 的歸因會被
   全盤採信,而其中至少 E108 是假陽性。
2. **A4 的配對設計**:第 1 輪看起來完美支持「改檔 → 失效」,第 2、3 輪直接推翻。
   只跑一輪就會發表一個反過來的操作規則。

### 觀測資料把「有效應」與「值得動」分開
