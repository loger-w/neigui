## 量測方法

| 項目 | 做法 |
|---|---|
| 管道 | `claude -p --output-format json`,每次都是全新 session |
| 核心指標 | `prompt_tokens = input_tokens + cache_creation_input_tokens + cache_read_input_tokens` |
| 為何是這三者之和 | 官方定義:「Total prompt size = input + cache_creation + cache_read」。cache 命中狀態會在 creation / read 之間搬動數字,**和是穩定的** |
| replicate | 每條件 2-5 次,報 median 與全距 |
| 噪音底線 | E01(同設定 n=5)全距 **6 tokens** → 儀器可解析 ≥10 tokens 的效應 |
| 無效判定 | 回覆含 `permission` 或 `permission_denials` 非空 → 該 run 硬失敗,不進統計 |

**兩次量測管道自身的失敗,都留在紀錄裡**(方法論價值高於結果):

1. **E16-E30 全批作廢** — 探針讀的檔在專案目錄外,headless 跳權限。徵兆是「基準(讀 1 行檔)比處置(讀 11KB 檔)還高」,物理上不可能,靠這個矛盾才發現。修法:檔案放進專案內 + `--allowedTools Read` + runner 自動判無效。
2. **`--allowedTools` 吃掉 prompt** — 它是變參旗標,位置參數放它後面會被一起吞,整批 ERR。修法:prompt 改走 stdin。

## 假說與結果

### H1 — 常駐層(每個 session 都付的錢)可量測且可關

**預測**:關掉 skill 來源會讓 prompt 縮小,幅度與被關掉的 description 總長度成正比。
**實驗**:E01-E06。
**結果**:**部分成立**。可量測(遠高於噪音),但幅度與直覺差很多。

| 條件 | Δ tokens | 佔 baseline |
|---|---|---|
| 8 支專案 skill 全關 | −76 | −0.2% |
| 10 支個人 skill 全關 | **+34** | +0.1% |
| superpowers plugin 停用(13 支)| −662 | −1.6% |
| chrome-devtools plugin 停用 | −124 | −0.3% |
| 全關(專案+個人+三 plugin)| −1,915 | −4.8% |

「關 10 支個人 skill 反而變大」是反常,交由 H2 追。

---

### H2 — skillOverrides 省下的 token 與 description 長度成正比(劑量反應線性)

**預測**:關 1 支 → x,關 4 支 → 4x,關 8 支 → 8x。
**實驗**:E07-E12(專案 skill 1/2/4/8 支;個人 skill 1/4 支)。
**結果**:**推翻**。

| 關幾支 | Δ tokens |
|---|---|
| 1(e2e-conventions)| +1 |
| 2 | +13 |
| 4 | −54 |
| 8 | −82 |

1-2 支時效應在噪音內;8 支時才 −82(≈ −10/支)。而 superpowers 整支 plugin 是 −51/支。**兩者差 5 倍**,說明 `skillOverrides` 移除的東西與停用 plugin 移除的東西不是同一份。

**推翻的價值**:如果照 H2 的線性假設外推「關掉 8 支長描述的專案 skill 可省上千 token」,會得到一個完全錯誤的優化方向。實測告訴我們 skill 清單根本不是成本熱點。

### H3 — CLAUDE.md 是常駐層最大單一成本

**預測**:砍 CLAUDE.md 的邊際效益高於砍 skill 清單。
**實驗**:E13-E15。
**結果**:**成立,且差距是量級等級**。

| 條件 | 原大小 | Δ tokens | 佔 baseline |
|---|---|---|---|
| 專案 CLAUDE.md → 3 行 | 10,288 chars | **−5,758** | **−14.3%** |
| user CLAUDE.md → 3 行 | 2,710 chars | −1,846 | −4.6% |
| 兩份都 → 1 行 | — | **−7,626** | **−19.0%** |

換算 **≈0.56 token / char**(中文為主的 markdown)。

> **這條推翻了 harness-context-slimdown 改版的前提。** 那次改版把力氣全放在 command 檔與 phase 細節分層,而 CLAUDE.md —— 佔常駐 prompt 19% 的那一塊 —— 被 §10 明文劃在 scope 外。真正的槓桿一直在 scope 外面。

### H4 — bytes 是 token 的有效代理

**預測**:bytes 降幅 ≈ token 降幅,所以拿 bytes 當 SC 門檻是合理的。
**實驗**:E31-E43(六個 command 檔 × 改版前後 = 12 個檔,各自量「讀進 context 的真實 token」)。
**結果**:**成立,且比值極穩**。

tok/byte 中位數 **0.455**,全距 [0.441, 0.468] —— 12 個檔跨 3,294B 到 20,938B,比值只波動 ±3%。

| 流程 | 改版前 tok | 改版後 tok | Δ |
|---|---|---|---|
| /feat | 9,419 | 5,191 | −44.9% |
| /mod | 2,378 | 2,128 | −10.5% |
| /perf | 1,895 | 1,746 | −7.9% |
| /bug | 1,559 | 1,541 | −1.2% |
| /refactor | 1,630 | 1,581 | −3.0% |
| /auto | 1,685 | 1,533 | −9.0% |
| **合計** | **18,566** | **13,720** | **−26.1%** |

與 SC-1 的 bytes 降幅(−27.5%)相差 1.4 個百分點 → **bytes 當代理是站得住的**。

**實驗**:E44 / E45(走到 Phase 3 各自要讀的檔集合)。
**結果**:**成立**。

| | 檔數 | bytes | tokens |
|---|---|---|---|
| 改版前(只讀 feat.md)| 1 | 21,117 | **9,353** |
| 改版後(feat.md + 6 支 ref)| 7 | 23,325 | **11,731** |

**+25.4%**。這與 SC-2 用 bytes 模型算出的「不降反增」方向一致,但這次是真實 token,且量測管道完全獨立。

### H8 — 砍常駐層對 opus coordinator 的省錢幅度 > 砍 command 檔

**預測**:成立。
**實驗**:E48、E52、E53、E55。

| 條件 | prompt | Δ vs E48 |

| opus 原況 | 43,358 | — |

### H9 — opus 的成本差異主要來自 prompt cache 命中狀態,不是 token 數

**預測**:成立(由 batch 4「每 token 成本差 2.5 倍」的異常引出)。
**實驗**:E56(同一條件連跑 4 次)。
**結果**:**成立,而且是整份研究裡最大的單一效應**。

| run | prompt_tokens | cost |
|---|---|---|
| 1 | 43,360 | **$0.2075** |
| 2 | 43,360 | **$0.0218** |
| 3 | 43,349 | $0.2074 |
| 4 | 43,360 | $0.0218 |

**token 數完全相同,成本差 9.5 倍。**

官方定價:cache **write = 1.25×** base input、cache **read = 0.1×** → 理論比值 12.5×。實測 9.5× 與之相符(output token 與未快取部分稀釋了比值)。

**推論**:任何讓 cached prefix 失效的動作,代價相當於把該次 session 的 input 成本乘上約 10 倍。而 prefix 是逐位元組比對的 —— **改任何一個 harness 檔就會讓下一次 session 付全額 write**。

### H10 — 同一檔在一個 session 內讀兩次,第二次仍全額計入

**預測**:成立(`load-manifest.json` 的「不去重」計帳規則就建立在這上面)。
**實驗**:E57 / E58。
**結果**:**成立,而且遠比「再計一次」更嚴重**。

| 條件 | prompt_tokens |
|---|---|
| 讀同一檔 1 次(11,194B)| 85,837 |
| 讀同一檔 2 次 | **137,663** |

差 **+51,826**,而該檔本身只有 5,193 token。差額來自**多出來的那一個 API turn 把整個 context 重送了一遍**。

**這條把 H7 的機制講清楚了**:prompt_tokens 是跨 API call 累加的,每多一個 turn 就把當下 context 全部再付一次。所以「省 context」的效益會被 turn 數放大 —— 一個 40k 的常駐層在 5 turn 的任務裡要付 5 次。

`load-manifest.json` 的不去重規則因此不只是成立,而是**低估**了重複讀取的成本。

### H11 — 同樣的總 bytes,拆成多檔比單檔貴

**預測**:成立(每次 tool call 有固定開銷)。
**實驗**:E59 / E60(內容逐位元組相同,只差檔數)。
**結果**:**成立**。

| 條件 | prompt_tokens | output_tokens |
|---|---|---|
| 單檔 15,328B | 87,544 | 285 |
| 同內容拆 7 檔 | 88,538 | **885** |

prompt **+994**(≈142/檔),output **×3.1**(模型逐檔敘述)。

**這是 H5 的機制解釋**:refs 分層變貴,一部分來自 bytes 微增,一部分就是這個每檔固定開銷 + 敘述放大。
