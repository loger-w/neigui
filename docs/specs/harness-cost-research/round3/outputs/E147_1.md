## 2. Context 被壓縮時的 fallback 路徑

去重之後,「Phase 1 讀過」這件事只存在於 context;compaction 會把它拿掉。fallback 分四層,由機械到自律:

**L0(永遠在,不受壓縮影響)** — `harness-context.py` 每個 SessionStart / UserPromptSubmit 都注入 slug / `current_phase` / gate / state 回寫狀態。壓縮後模型仍知道自己在 Phase 4。這是所有 fallback 的錨。

**L1(磁碟事實)** — 進 Phase 2 / Phase 4 的**第一個動作**:Read `state.json`,看 `refs_loaded`。
- 欄位有 `review-protocol.md → 1`,且自己**能複述** A 節五步 / B 節 (a)-(d) → 不重讀,直接開工。
- 欄位有,但**複述不出來** → 判定已被壓縮,走 L2。
- **欄位缺失 / 為 `{}`** → 保守視同沒讀過,走 L2(對齊 review-protocol C 節「無法證明就重做」的既有精神)。

**L2(重讀,只讀需要的那份)**
1. Read `~/.claude/harness/refs/review-protocol.md`(4,090 bytes)—— 這份是 dispatch 與快篩紀律,壓縮後**一定**要重讀。
2. `superpowers:receiving-code-review` 全文(6,203 bytes)**預設不重讀**:feat.md 的 Receiving 卡在 command 檔裡,而 command 檔在壓縮摘要中通常被保留;先確認卡在不在(自檢:能否列出六條)。卡在 → 只補 L2-1。卡也不在(極端壓縮)→ 才呼叫該 skill。
3. 任一次重讀 → append `state.json.refs_reloaded`(`{path, phase, reason: "compacted"}`)+ 回寫 `last_updated`。

**L3(自檢失效的兜底)** — 若在 Phase 2/4 發現自己已經開始分類 finding 卻答不出「三分類值是哪三個」,直接停下走 L2,不繼續憑感覺分類。這條是自律點,誠實標為殘餘風險(見 §4.5)。

> 為什麼不靠 hook 在 phase 2/4 提醒?因為那正是重複的來源:hook 一提醒模型就照讀,去重立刻回歸。`condition` 欄同時關掉 hook 提醒與預設帳,fallback 改由「state.json + command 常駐文字」承擔 —— 兩者都不受 context 壓縮影響。

**(c) 內容覆蓋對照表**(人工一次性,落檔 evidence) — 逐條列出 `receiving-code-review/SKILL.md` 的 11 個小節,標「進卡 / 刻意留全文 / 情境不適用」,並對「刻意留全文」的三塊寫明「/feat 的哪個情境會需要 → 走 §2 L2-2 讀全文」。**任何一條標成「情境不適用」都要寫理由**(例:GitHub thread replies —— /feat 的 reviewer 是 agent,round JSON 落檔,無 PR inline comment thread)。這張表是「壓縮版沒有偷偷刪掉紀律」的唯一書面證據。

**(d) 行為級 smoke(必跑,不可只靠靜態)** — 拿一個既有 feature 的 artifact 重放,或用下一個真實 `/feat` 收第一輪:
1. 三輪各自的 round JSON 仍產出:`design-review-round-1.json` / `impl-spec-review-round-1.json` / `code-review-round-1.json` 三檔存在。
2. 每檔每條 finding 有 `resolution`,且 `resolution.classification ∈ {accepted, rejected_with_reason, needs_more_context}`:
   ```bash
   python - <<'PY'
   import json, glob
   ok = {"accepted","rejected_with_reason","needs_more_context"}
   for f in glob.glob(".claude/feat/*/["dic"]*review-round-*.json"):
       for x in json.load(open(f, encoding="utf-8")):
           assert x.get("resolution",{}).get("classification") in ok, (f, x)
   print("resolution schema OK")
   PY
   ```
3. **反 performative 抽驗**:三輪合計至少出現 1 條 `rejected_with_reason` 且理由是技術性的(引用檔案/行號/既有行為)。**全部 accepted = 紅旗**(卡的第 2、4 條沒生效),回頭補卡文字,不算通過。
4. Phase 4 的 transcript 中**不得出現**對 `superpowers:receiving-code-review` 的第二次 Skill 呼叫;若出現,檢查 `refs_reloaded` 有沒有對應紀錄 —— 有紀錄 = fallback 正確啟動(合格);無紀錄 = 去重沒生效(不合格)。

**驗收判準(全部成立才算改對)**:3.1 三項達標 + 3.2 全綠 + 3.3 (a)(b) 零違反 + (c) 表落檔 + (d) 四項通過。

## 4. 這個改動可能打壞什麼

按嚴重度排序,含緩解與偵測方式。

**4.1(最可能)壓縮後靜默漏讀 → Phase 4 的 review 品質降。**
去重把「內容一定在 context」換成「內容曾經在 context」。極長 session(`/feat` 中位 300+ turn)壓縮機率不低,而判斷「我還記不記得 B 節四條快篩」本身是自律點,模型可能自認記得而其實已丟失。
→ 緩解:§2 的 L1 用 `state.json.refs_loaded` 把判斷從「記憶」改成「讀檔 + 自我複述」;L2 缺欄位時保守重讀。
→ 偵測:`refs_reloaded` 長期恆空 + review 品質下滑 = 自檢沒在跑。第一個真實 `/feat` 跑完要人工看一次這個欄位。

**4.2 harness-context.py 在 Phase 4 不再輸出 refs 行。**
phase 4 的兩個 ref 改 conditional 後,`refs_for_phase(4.0)` 回 `[]`(`feat-phase4-fix.md` 本來就是 conditional),第四行整段消失。Phase 2 仍有 `feat-phase0-2.md`,不受影響。
→ 這是**預期副作用**,不是 bug:hook 提醒正是重複載入的驅動力。但代價是 Phase 4 少了一個每回合的機械錨,只剩 feat.md 常駐文字。
→ 現有 `test_hook_omits_refs_line_when_phase_has_no_refs` 用 phase 5 驗此行為,不會紅。

**4.3 `feat-L` 的 AFTER 數字改變 → 既有 SC 基準線失真。**
`docs/specs/harness-context-slimdown/` 的 SC-1/SC-2 用 `--before feat-L-before --after feat-L` 求降幅;本改動會讓降幅變大,舊驗收輸出與新輸出對不上。
→ 緩解:`feat-L-before` **不動**;在 slimdown spec 的驗收檔追一行「20XX-XX-XX receiving 去重後降幅更新為 X%,原始驗收數字見 commit <sha>」。不要回頭改舊 evidence 檔(那是歷史證據)。

**4.4 卡與全文漂移(未來 superpowers 更新 receiving-code-review)。**
plugin 更新後全文可能新增紀律,而 feat.md 的卡不會自動跟。
→ 緩解:dispositions 只能釘存在性,釘不了「內容一致」。務實做法:在 feat.md 卡末尾註明對照的 skill 版本/日期,並把「plugin 更新後複查 Receiving 卡」寫進 `docs/next-time.md`。**明確標為殘餘風險,不假裝解決了。**

**4.5 語意 gate 本來就無法機驗(既有邊界,本改動使其更吃緊)。**
SPEC.md §9 已承認「harness 保證的是必被執行 + 留痕,不是品質」。去重讓 Phase 4 的 receiving 品質更依賴模型智力(卡 vs 全文)。弱模型時代,壓縮版可能不足以壓住 performative agreement。
→ 偵測:§3.3(d)3 的「全部 accepted = 紅旗」是唯一可機驗的代理指標。連續兩個 feature 都零 `rejected_with_reason` → 回滾本改動(見 4.8)。

**4.6 `condition` 欄語意被借用。**
原設計中 `condition` 意思是「這個 phase 不一定會發生」(如 per_file 模式、收尾撞異常),本次借用成「壓縮才需要」。兩者在求和與注入行為上等價,但語意混用會誤導下一個讀 manifest 的人。
→ 緩解:condition 字串寫得夠白(「context 已壓縮、Phase 1 那份不在時才重讀」),且 §1.4 檔頭有對應說明。可接受的取捨 —— 另開 `reload_only_if_absent` 新欄要同步改兩支 hook + 測試,收益不抵風險。

**4.7 `feat.md` 常駐 context 變大 +~880 bytes。**
這是無條件成本(每 session 都付),換取 −20,586 的條件成本。淨帳仍大幅為正,但方向上與「command 只留觸發偵測層」的分層原則相反 —— 這次是刻意例外:**跨三個 phase 共用的紀律放常駐,才是分層原則的正確結論**(refs 層的前提是「不到那個 phase 不必讀」,而 receiving 是三個 phase 都要)。

**4.8 回滾路徑。**
單一 commit,`git revert` 即可;四個 manifest 條目移除 `condition`、feat.md 三處還原,系統回到今天的行為。回滾判準:§4.5 的紅旗連兩次,或 §3.3(d) 任一項不通過且兩次修不好(鐵則 F)。
