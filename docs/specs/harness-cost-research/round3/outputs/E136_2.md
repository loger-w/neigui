# Change-spec:feat-L review 說明書 load-once 化

## 0. 根因與設計原則

**根因**:載入指令寫在「每個 phase 的就地指路」裡,而不是「每 session 一次」的層級。Phase 1、2、4 各自無條件觸發 Read `review-protocol.md` + invoke `receiving-code-review`,即使內容還在 context。

**設計原則**:
1. **Load-once + 沿用**:兩份說明書每 session 各載一次,後續 phase 沿用 context 內既有內容。
2. **Fail-safe 方向 = 重載**:自檢「內容是否還在 context」不確定時一律重讀。失守的最壞情況是回到舊成本(多讀一次),永遠不是弱化 review。
3. **三輪 review 的 dispatch、退出條件、輪數上限、receiving 三分類要求逐字不動** —— 只改「說明書怎麼進 context」。
4. **不抄 skill 內容進 harness refs**:receiving-code-review 是 superpowers plugin 的檔,抄摘要進來會跟上游 drift;省法只能是「不重複載」,不是「換成短版」。

**誠實預估**:穩省的是 Phase 2 那兩份(緊鄰 Phase 1,壓縮機率低);Phase 4 隔著整個 Phase 3 TDD,compaction 後 fallback 觸發率預期偏高,那兩份「視 session 長度」。帳按省 10,222~20,444 bytes 計,不宣稱一定全省。

## 2. Fallback 路徑(context 已被壓縮 / 內容不在時)

| 情境 | 觸發點 | 行為 |
|---|---|---|
| 同 session,無壓縮 | Phase 2/4 自檢 | 全文仍在 → 沿用,不重載(省下的就是這裡) |
| 同 session,compaction 已把全文換成摘要 | Phase 2/4 自檢 | 摘要 ≠ 全文 → 重讀 ref / 重 invoke skill |
| 自檢**不確定**(摘要提過「已讀過該檔」但內容殘缺) | 同上 | **視同不在,重載** — 判準明寫「不確定 → 重讀」,堵住「我記得大概」這條路 |
| 跨 session resume(state.json 從 Phase 2/4 續跑) | 進場即自檢 | Fresh context 必然不過 → 重載。**刻意不在 state.json 記 loaded flag**,否則持久化的 flag 會騙過 fresh context |

關鍵性質:所有 fallback 分支的終點都是「重載」,不存在任何分支的終點是「跳過 receiving 紀律」或「跳過協定」。

## 3. 驗證方式

### 3a. 證明改對了(重複消除)

1. **靜態 grep**:`feat.md` 中 Phase 2/4 不再有無條件的「依 `refs/review-protocol.md`」與「呼叫 `superpowers:receiving-code-review`」;每個沿用點都指向「載入紀律」。鏡像與原件 `diff` 逐 byte 一致。
2. **帳面重算**:對 `feat-L` 無條件 entries 求和(沿用 manifest `_comment` 的「求和不去重」規則),after − before = **−20,444 bytes**(2×4,090 + 2×6,132)。同時確認 `batch_b_spec.py` 等既有分析腳本對 `condition` 欄位的處理方式(排除或另計),避免成本研究對照被歪掉。
3. **行為實測**(round3 的量測方法):跑一次不觸發 compaction 的 feat-L session,transcript 中 `review-protocol.md` 的 Read 恰 1 次、`receiving-code-review` 的 Skill invoke 恰 1 次。
4. **Fallback 實測**:偽造 `state.json` `current_phase: 4` 開 fresh session resume → 應觀察到重讀 + 重 invoke(證明 fallback 真的會走,而不是憑殘影繼續)。

### 3b. 證明三輪 review 沒被弱化

1. **Diff 紀律**:改動 diff 只落在 §1 列出的行;Phase 1/2/4 的 dispatch 指令、退出條件(無 P0 且 P1 ≤ 2)、3 輪上限、雙焦點、receiving 三分類定義**逐字未變** — 用 diff 逐段核對。
2. **機械可查的執行證據**:receiving 紀律被執行的落檔證據是 review round JSON 每條 finding 的 `resolution` 欄位(review-protocol A 節 step 4 要求,本次不動)。測試 run 後檢查:三輪 review 各有 round JSON、每條 finding 都帶 `resolution` ∈ {accepted, rejected_with_reason, needs_more_context}。這個證據**不依賴 skill 被 invoke 幾次**,直接量測紀律輸出。
3. **對照組**:與 round3 既有 session 的 review JSON 結構比對,欄位齊全度不得下降。

## 4. 可能打壞什麼

1. **F2 風險(prompt 自律規則實測會失守)**:「不重讀」本身就是自律規則。失守有兩個方向 —
   - 多讀(自檢過度保守)→ 回到舊成本,無害,只是省不到;
   - **憑殘影執行**(自檢誤判「還在」但其實只剩 compaction 摘要)→ receiving 分類品質下降。這是本改動唯一真正的弱化路徑。緩解:(a) 判準明寫「不確定 → 重載」;(b) `resolution` 欄位缺失 / 三分類走樣可被 Phase 8 tag 驗證與收尾 review 機械抓到。建議下一輪 harness-cost 量測加一個「Phase 4 finding 的 resolution 欄位齊全率」指標確認沒退化。
2. **Phase 4 實際省不到**:Phase 3 很長時 compaction 幾乎必發生,phase 4 兩份會走 fallback 重載。這不是 bug,但如果帳按全省 20,444 記就是虛報 — manifest `_note` 已明寫,量測報告也要按實際觸發率記。
3. **鏡像漂移**:只改一邊(`docs/harness/` 或 `~/.claude/`)。必須同 commit 成對改,驗證 3a-1 的 diff 一致性擋這條。
4. **其他 profile 帳面不一致**:`mod-M`(phase 3/5)、`bug`、`refactor`、`perf` 也載 `review-protocol.md`,新「載入紀律」節是通用語義,它們的 manifest entries 卻仍是無條件 — 帳面暫時高估這些 profile 的成本。本次不動(scope 紀律),寫進 `docs/next-time.md`。
5. **分析腳本相容性**:若 `batch_b_spec.py` / results 統計不認得 `condition` 欄位或把它當無條件計入,before/after 對照會失真 — 驗證 3a-2 前置檢查。
6. **上游 skill 改版**:superpowers 更新 receiving-code-review 時,新版內容自然在下次 invoke 進 context,無 drift 風險(因為我們刻意不抄內容);唯一要求是不要有人日後「順手」把摘要抄進 refs — 已在 §0 原則 4 明文。
