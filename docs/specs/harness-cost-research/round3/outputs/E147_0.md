## 0. 目標與非目標

**目標**:`harness/refs/review-protocol.md` 與 `superpowers:receiving-code-review` 在一個 `/feat` session 內各只進 context 一次(現況各三次),省下 20,444 bytes 與**兩個純 Read turn**。

|---|---|---|---|
| **R1** | `--before feat-L-before --after feat-L` 的降幅混入「記帳語意改變」,不是真實省下 | 對外報的數字失真(這個 harness 上個月才因為命名誤導被打臉一次) | `feat-L-before` **不加 `repeat_of`**;報數時強制分列「舊語意 129,332 / 新語意 108,888 / 差額 20,444 全部來自 dedup」,並附 `--count-repeats` 的可重現輸出 |
| **R2** | ledger 假陽性:檔案說已載入,實際內容已不在 context | receiving 憑印象跑 → **這是本改動最危險的失效** | SessionStart 一律清空(不只 compact);§D 的判定句 + 記憶錨當第二道;失效方向設計成 fail-open 多讀 |
| **R3** | PostToolUse 對 `Skill` 工具可能不觸發,或 payload 欄位名與假設不同 | `skill:receiving-code-review` 記不進 ledger | 只影響「省不省」,不影響 review(注入行不管 skill)。實作時先用一次真呼叫驗 payload;不觸發就只保留 `Read` 側,receiving 的 one-shot 純靠文字層,並依 F2 先例**誠實把 6,203×2 計回 after 側** |
| **R4** | hook 寫 `state.json` 會更新 `last_updated`,掩蓋 `harness-stop-audit.py` 的 lagging 判定 | 強制層被自己人弱化 | ledger 存**獨立檔** `refs-loaded.json`,state schema 零改動;新增測試釘死「跑完 ledger hook 後 state.json 位元組不變」 |
| **R5** | ledger 檔進了 artifact commit / 版控噪音 | Phase 8 commit 多一個沒意義的檔 | `.claude/feat/<slug>/` 全目錄本來就在 `.git/info/exclude`;Phase 8 artifact commit 時明確排除 `refs-loaded.json`(寫進 `refs/feat-phase8.md` 的排除清單) |
| **R6** | §D 讓 review-protocol.md 變大約 900 B,而該檔被五個 command 共用 | mod/bug/refactor/perf 各多 ~900 B | 淨值仍為負(mod-M 自己就有 review-protocol ×2 + receiving ×1 的同型重複,可用同一機制在後續處理);本次**不動 mod/bug/refactor/perf 的 manifest**,Scope 紀律 |
| **R7** | session 期間有人改了 review-protocol.md(改 harness 本體的 session),ledger 讓 agent 用到過期內容 | 用舊協定跑 review | §D 判定第 3 條明寫;改 harness 的 session 手動刪 ledger。列 Known Risk |
| **R8** | 鏡像沒同步 → `docs/harness` 與在役版本漂移 | 履歷素材與實況不符 | sync 腳本 + 17 個測試已是既有防線,列進 4.4 必跑 |
| **R9** | **注意力衰減**:Phase 4 不再重讀,模型「有」但注意力權重下降,receiving 品質靜默滑落 | 三輪 review 形式在、實質弱化 | **本改動的核心殘餘風險,無法機械驗證**。緩解:§D 記憶錨 + Phase 4 產出的 `resolution` 欄可抽驗 + canary 觀察(4.1 第 4 條)。明文寫進 design 的 `## Known Risks`,不假裝零風險 |
| **R10** | 新增第 10 個 hook,強制層自身複雜度上升(「強制層有 bug 比沒有更糟」) | hook 壞掉影響所有 session | 新 hook 全程 fail-open、exit 恆 0、無 active feature 零副作用;TDD 紅先行 + 4 個測試;最小回退 = 拔掉註冊 |

## 6. 成功條件(SC,附量法)

| SC | 條件 | 驗證方式 |
|---|---|---|
| SC-1 | 一次 L 級 /feat 的 Phase 1→4,`review-protocol.md` 與 receiving skill 各只進 context 一次 | canary session 的 `refs-loaded.json` + transcript tool-call 計數 == 1 / 1 |
| SC-2 | 因載入協定而起的 turn 由 6 降到 2 | 同上,計 Read/Skill tool call 數(turn 是乘數,主指標) |
| SC-3 | 載入帳 129,332 → 108,888(−20,444,−15.8%) | `harness_load_estimate.py --profile feat-L --scope main`,含 `--count-repeats` 對照 |
| SC-4 | reviewer 側零 diff、subagent scope 位元組不變、dispositions `VIOLATIONS n=0` | §4.1 第 1-3 條指令 |
| SC-5 | 壓縮 fallback 可觸發 | §4.3 兩段 echo-pipe 反證實驗 |
| SC-6 | hooks pytest 全綠(≥164)、鏡像同步測試綠、backend pytest/ruff 不受影響 | §4.4 |
| SC-7 | canary session 三種 round JSON 齊全且每條 finding 有實質 `resolution` | Phase 8.5 人工抽驗,結果寫收件匣 |

SC-1 / SC-2 / SC-7 的驗證窗口 = **下一次真實 L 級 /feat**(非 anytime);窗口外的降級策略:先以 §4.3 的合成 payload 驗機械層,SC-1/2/7 標 `pending canary` 掛 `docs/next-time.md`,不得用「應該可以」結案。
