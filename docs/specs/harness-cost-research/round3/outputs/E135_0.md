## 1. 拍板方案

**把 receiving 紀律寫成 harness 自製的 §D,內嵌進 `review-protocol.md`,顯式覆寫掉 `superpowers:receiving-code-review` 的載入。**

選這個而不是別的,理由三條:

1. **零額外載入動作**。phase 1 / 2 / 4 本來就各載一次 `review-protocol.md`;§A step 4、§B、§C 每一處引用 receiving 的地方都在這個檔裡 —— 兩者永遠同時被需要,合檔是正解,不是塞東西。
2. **不靠自律**。「Phase 2 沿用 Phase 1 已載入的內容」這種寫法,依 round 3 F2(靠 prompt 自律的規則實測失守,manifest 自己第 49 行就記著 SC-8 FAIL 的先例)不可信;唯一機械上站得住的省法是**把每次都會被重讀的東西縮小**,而不是假設它不會被重讀。
3. 順帶補上 §C 那個「引用了沒載入」的漏洞,/bug /refactor /perf 收尾第一次真的拿得到 receiving 紀律。

**明確不做**(scope 紀律 B,寫進 `docs/next-time.md`):不拆 `review-protocol.md`。剩下那 8,038 重複的根因是 phase 1/2 只用 §A、phase 4 只用 §B,卻整檔載入;要消除必須拆成 `review-spec.md` / `review-code.md`,爆炸半徑是 5 個 command + branch-lifecycle + 4 個 profile + dispositions,預估再省約 7 KB。與本次改動正交,可獨立做。

### 2.1 `~/.claude/harness/refs/review-protocol.md` —— 檔尾新增 §D

在現行 §C 之後追加(§A/§B/§C 一字不動):

```markdown
## D. Receiving 協定(所有 review 意見的接收紀律)

`RECV-PROTOCOL-v1` — 本節是 harness 自製的等價精簡版,**顯式覆寫**「呼叫
`superpowers:receiving-code-review`」:A / B / C 節任一步收到的 finding 一律用本節處理,
不另載該 skill(上游完整版 pin `<superpowers>/skills/receiving-code-review/SKILL.md`
@6.2.0;只有本檔讀不到、或爭議已進到輪數上限仍卡住,才升級去讀)。

**逐條三分類**(每條 finding 必填 `resolution`,禁止整批 accepted):

- `accepted` — 已用 grep / Read / 測試在**本 codebase** 反證為真,附證據來源。
- `rejected_with_reason` — 附技術理由,合法理由僅這幾類:打壞既有行為 / reviewer
  缺脈絡 / YAGNI(grep 無 caller)/ 本 stack 不成立 / 相容性 / 與 user 既有架構決策相左。
- `needs_more_context` — 驗不動就說驗不動,不猜著改。

**四條硬規**:

1. **驗證先於實作** — 沒對照 codebase 反證過的 finding 不准動手。
2. **不明確就停** — 任一條看不懂 → 停下問 user,不先做懂的那幾條(finding 常相關,
   半懂 = 改錯)。與架構決策衝突同樣停下問。
3. **不表演式同意** — 禁「你說得對」/「好建議」/「感謝指出」;只寫「已修:<改了什麼>」
   或技術性反駁。自己反駁錯了,一句話認並改,不長篇道歉、不辯解。
4. **一次一條、逐條驗** — 順序:blocking(壞行為 / 安全)→ 簡單修 → 複雜修;每條修完
   跑對應測試再進下一條,不整批 add / commit。
```

**刻意不收錄**(對照表,供 review 判「有沒有弱化」):上游的 GitHub inline reply API 用法(本 harness 的 review 不走 GitHub thread)、「Real Examples」四個對話範例(示範性、非可執行條目)、Common Mistakes 表(每列都已被四條硬規涵蓋)。上游的 8 個可執行條目(response pattern / forbidden responses / unclear→STOP / external reviewer 五問 / YAGNI grep / implementation order / when to push back / 認錯寫法)**逐條對應**進 §D。

## 3. Context 被壓縮後的 fallback 路徑

分四層,**第一層是機械的,不靠自律**:

| 層 | 觸發 | 路徑 | 前提 |
|---|---|---|---|
| L1 機械重指路 | 每次 SessionStart / UserPromptSubmit | `harness-context.py` 讀 `state.json.current_phase` → `harness_lib.refs_for_phase()` 從 manifest 取該 phase 的 `harness/refs/*`(scope=main、非 conditional)→ 印「此 phase 的 refs:~/.claude/harness/refs/review-protocol.md」 | 有 active `.claude/feat/<slug>/state.json` 且 `current_phase` 正確。**phase 1/2/4 的 review-protocol 三筆都是無條件的**,L1 天然涵蓋 |
| L2 自檢 token | 分類動作開始前 | 說不出 `RECV-PROTOCOL-v1` 的三分類 + 四條硬規 → 判定已被壓縮 → **重讀 `review-protocol.md`**(≤6.4 KB) | feat.md 核心原則那句(2.3a)在 context 內。這層是自律,只當 L1 的補網 |
| L3 command 檔指路 | 非 /feat 流程(無 state.json,L1 零輸出)的 ad-hoc review | `feat.md` / `mod.md` / `branch-lifecycle.md` 的內文引用寫明「依 review-protocol D 節」,照路徑 Read | command 檔本身在 context(它是 phase=None 常駐載入) |
| L4 升級 | `review-protocol.md` 讀不到 / §D 不存在(檔案被改壞、跨版本 revert) | 才呼叫 `superpowers:receiving-code-review`(路徑 pin 在 §D 檔頭),並寫 `state.json.receiving_fallback: "superpowers"` | — |

L4 觸發即在 Phase 8.5(B)流程瑕疵候選登記一筆 —— 走到 L4 代表 L1/L2 失效,那是要修的訊號,不是可接受的日常路徑。

**明確的取捨**:本方案不承諾「phase 2/4 不會再讀」。壓縮後重讀是預期行為,省的是**每次重讀的體積**(10,222 → ≤6,419)。任何寫成「已載入過就不必再讀」的規則,依 F2 都會失守,不列入省下的帳。

## 5. 這個改動可能打壞什麼

1. **`using-superpowers` 的「1% 可能適用就必須 invoke」會把 skill 又拉回來。**
   這是最可能的失敗模式,且有前例:manifest 第 48–49 行記著 `subagent-driven-development` 的同型覆寫 SC-8 FAIL(只有負向指示、無機械 gate → 實測失守,誠實計入 after 側)。緩解是 2.3a + 2.4 的雙點硬措辭;**若 R6 觀測到 >0 次,升級為 PreToolUse hook**(在 `protect-harness.py` 旁新增:有 active feat state 時 `Skill(receiving-code-review)` → deny + 提示改讀 §D)。該 hook 動 `~/.claude/hooks/`,會被 `protect-harness.py` 自己 ask,且要補 hook 測試 —— 成本不低,所以先觀測再決定,不預先做。
   **最壞情況**:失守 → 省不到,但也不會比現況差(§D 只多 2.4 KB)。

2. **上游 superpowers 升版後 §D 漂移。** §D pin 了 6.2.0;升版時沒人比對就會出現「harness 說一套、上游改了另一套」。緩解:§D 檔頭寫死版本號,並在 Phase 8.5(C)meta-review 檢查清單加一條「superpowers 版本變動 → 比對 §D 對照表」。

3. **`review-protocol.md` 是 9 個 profile 共用的熱檔,變胖是全域成本。** /bug /perf 各 +≤2.4 KB、/refactor +≤4.8 KB,這幾條沒有對應節省。已列在 §1 的帳裡,不藏。

4. **/bug /refactor /perf 收尾的行為會變。** 它們現在第一次真的拿到 receiving 紀律,收尾 review 會開始出現 `rejected_with_reason` 而不是照單全收 —— PR body 的「review 結果摘要(finding 數 + 分類)」數字會變。這是修好漏洞,但**別把它誤判成 regression**。

5. **跨改版的進行中 /feat。** 若有 active feature 已跑過 phase 1(讀舊指示)而 phase 4 讀到新指示,會混用兩套來源。落地前先 `ls .claude/feat/*/state.json` 確認無 active feature;有的話等它收尾,或明確告知並接受該次混用。
