## 2. Fallback:context 被壓縮時的路徑

寫進 feat.md 核心原則(hunk F),原文如下:

```markdown
  **§fallback — 下列任一成立就重讀,重讀不算違規,漏讀才是**:
  (a) **複述測試失敗**:進 Phase 2 前說不出 A 節 5 步(dispatch typed reviewer / 傳路徑不傳內容 /
      round≥2 附上輪 JSON / 逐條 resolution / 計數+1 重跑),或進 Phase 4 前說不出 receiving
      三分類與六條硬規則 → 重讀對應的 `refs/review-protocol-spec.md` 或呼叫 skill。
  (b) **context 已壓縮**(對話由摘要接手、或本檔本文已不在窗口):
      L1 先重讀 `~/.claude/commands/feat.md` —— 本檔含完整 Receiving 契約,多數情況到此為止;
      L2 本檔重讀後仍不足(例如需要 A 節 5 步細節)→ 重讀該 phase 對應 ref;
      L3 仍無法判定某條 finding 的分類 → 才呼叫 `superpowers:receiving-code-review` 讀完整判例。
      **順序不可跳** — L1 的成本遠低於 L3,跳級等於白省。
  (c) **邊界 finding**:某條 finding 在 accepted / rejected 之間拿不定,或反駁理由寫不出技術根據
      → 直接走 L3,不准為了省 context 硬分類。
  **反模式**:不得把「已載入」寫進 state.json 再據以免讀 —— 記錄還在不代表內容還在,
  那會把 load-once 變成靜默漏讀。state.json 只記 phase / 計數,不記載入狀態。
```

補強機制(非 feat.md 本體):`harness-context.py` 的 phase 注入行每回合重印,而它的內容由 manifest 的 `phase` 欄產生 —— 改後 Phase 2 的 refs 行不再列 review-protocol(正確,因為 base case 不該重讀),Phase 4 仍會列 `review-protocol-code.md`。**Phase 2 的指路只剩 feat.md 就地句**,所以 hunk D 的就地句是必要的(見 §4 風險 1)。

### 3.6 三輪 review 沒被弱化(行為層,必做)

靜態只能證明「沒被刪」,不能證明「還會發生」。跑一支真實的 S 或 M 級 `/feat`(建議從 `docs/next-time.md` 取一項小改動)走完 Phase 1→4,附以下證據:

1. `.claude/feat/<slug>/` 下三份 round JSON 存在:`design-review-round-1.json`、`impl-spec-review-round-1.json`、`code-review-round-1.json`;貼出各檔 findings 數。
2. 三份 JSON 的**每條 finding 都有 `resolution` 欄**,且分類值落在三分類內;整體至少出現一條 `rejected_with_reason` 或 `needs_more_context` —— 證明 receiving 沒退化成「照單全收」(全 accepted 且無反駁理由 = 紅旗,即使測試全綠也判 FAIL,回頭檢討 anchor 六條是否壓縮過頭)。
3. transcript 檢查:Phase 2 全程**沒有**第二次 Read `review-protocol-spec.md`、Phase 2/4 **沒有** Skill 呼叫 `receiving-code-review`(base case 成立)。
4. **fallback 反向驗證**(不可略):另跑一次刻意在 Phase 1→2 之間觸發 compaction 的 session(或手動以 `/clear` 後只餘 state.json 的情境模擬),確認 agent 走了 L1(重讀 feat.md)並完成 Phase 2 review,必要時走 L2。fallback 沒被觸發過就等於沒驗過,不能算完成。

---

## 4. 這個改動可能打壞什麼

依「真實風險 × 是否可偵測」排序:

1. **Phase 2 的 review 靜默消失(最高風險)。** `harness_lib._phase_refs` 從 manifest 產生每回合的「此 phase 的 refs」注入行;刪掉 phase 2 的非條件條目後,Phase 2 的注入行不再提 review-protocol。若 agent 實際上是靠這行指路而非靠 feat.md 就地句,Phase 2 可能整輪跳過 review。
   - 緩解:hunk D 的就地句保留完整指路 + dispatch 對象;§3.6 的行為驗證以 `impl-spec-review-round-1.json` 是否產出為判準。
   - 偵測:該檔不存在 = FAIL,無法靠靜態檢查抓,必須跑 §3.6。

2. **receiving 品質退化,且靜態不可偵測。** 6,203 B 的完整判例壓成 ~900 B 的六條,必然丟掉判例細節(pushback 措辭、GitHub thread reply、糾正自己反駁的寫法)。若 Phase 4 遇到需要判例的 finding 而 agent 沒觸發 fallback (c),可能退化成「一律 accept」或「一律 reject」。
   - 緩解:fallback (c) 明文「拿不定就走 L3,不准為了省 context 硬分類」;§3.6 判準 2 的分類分佈當持續監看指標。
   - 這是本改動**唯一無法用檢查完全消除**的風險,寫進 `design.md` Known Risks。

3. **anchor 與 skill 漂移。** superpowers 升版改了 receiving 流程,feat.md 的常駐六條不會跟著動,且沒有任何機制會發現。
   - 緩解:anchor 標註「壓縮自 receiving-code-review(2026-07-26 版)」;Phase 8.5 meta-review 檢查清單加一項「superpowers 版本變動時重核 anchor」。

4. **拆檔造成的協定漂移。** 原本「單檔 = 所有 review 的單一協定」的好處消失,日後可能只改 spec 檔忘了 code 檔。
   - 緩解:三檔互指檔頭 + dispositions 各留一條 present check + §3.5(d) 的還原比對做為一次性基準。

5. **跨 command 連帶改動。** mod / refactor / bug / branch-lifecycle 的路徑引用共 5 處,漏一處就是死連結。`harness_load_estimate.py` 會對 manifest 漏改 exit 2(好),但 **command / skill 檔內的死連結它抓不到** —— 只有 §3.4 的 grep 抓得到。漏改的後果是該 command 執行到那步 Read 失敗。

6. **其他 profile 的降幅數字被動變動。** `mod-M` / `refactor` / `bug` / `perf` 的 after 側因拆檔而縮小,但它們的 `*-before` 側沒有 review-protocol,於是 `REDUCTION pct` 會**看起來變好**卻不是流程改善所致。不處理會讓 round 3 的結論失真。
   - 處置:重跑四組 before/after 並在 RATIONALE.md 明註「pct 變動含拆檔的機械效應,非流程精簡」。

7. **dispositions 的 present check 打在不存在的檔上。** row 13/21 若忘了改 file,`verify_dispositions` 會回報「檔案不存在」violation → exit 1。這是**期望行為**(§3.2 的中間態就是要它紅),但別誤判成改壞了。

8. **`protect-harness.py` 會攔 `~/.claude/hooks/**` 的寫入(ask 不 deny)。** §3.3 新增測試檔會觸發核准提示;`~/.claude/commands/`、`~/.claude/harness/` 不在守備範圍,不會被攔。這是流程摩擦不是破壞。

9. **鏡像與 worktree 殘影。** `.claude/worktrees/*/docs/harness/` 下有舊副本,不同步不影響在役 harness,但日後從那些 worktree 做比對會看到舊結構。不處理,記進 `docs/next-time.md`。

10. **`feat-L-before` 若被順手改動,SC-1/SC-2 的降幅全部失真。** 明令不動;§3.5(a) 的 diff 白名單應同步涵蓋 manifest —— `git diff` 內出現 `feat-L-before` 區塊即 FAIL。
