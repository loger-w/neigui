# change-spec:feat-L review 說明書單次載入

**slug**:`harness/review-refs-load-once`
**類型**:🔴 行為改動(harness 載入行為)+ 🟢 新增 hook 提示與測試
**不動的東西**:Phase 1 / Phase 2 / Phase 4 三輪 review 的 dispatch 對象、criteria、輪數上限、退出條件、round JSON 產物、receiving 三值分類義務 —— 全部字面零改動。

---

## 1. 問題定義(改動前的事實)

`load-manifest.json` 的 `feat-L` profile 對同兩支檔各列三筆(phase 1 / 2 / 4),manifest 註解明寫「求和不去重(每次 Read 都真的佔窗口)」—— 也就是說這三筆是**誠實記帳**,不是帳目 bug:feat.md 現在確實叫模型在三個 phase 各讀一次。

三輪 review 的**對象**不同(design.md / PLAN.md / 實作 diff),但「怎麼接收 review 意見」與「review 協定本身」是同一份說明書,第二、三次進 context 是純重複。

---

## 2. 設計決策(先講,因為逐檔修改是它的推論)

**D1 — 無條件載入點綁「首個實際發生的 review 迴圈」,不綁 Phase 1。**
feat.md 明寫 Phase 1「S 跳過 / M 1 輪」。硬綁 Phase 1 的話,S 級跑起來會完全沒有載入點。因此 feat.md 措辭寫「Phase 1 → 若跳過則 Phase 2 → 再跳過則 Phase 4」,而 `feat-L` profile(L 級一定跑 Phase 1)把無條件那筆掛在 phase 1。**代價**:S/M 沒有對應 profile,帳面抓不到這個洞 —— 列為 Known Risk(§5.2)。

**D2 — 省下的是「必然重複」,不是「可能重複」。**
phase 2 / 4 那四筆改成帶 `condition` 的條目,不是刪掉。`harness_load_estimate.py` 對 `condition` 條目的既有語意就是「非 worst 不計、`--worst` 計」,正好對應「正常路徑不重讀、壓縮/resume 路徑重讀」。所以**驗收要同時看兩個數**:非 worst 降 20,444,worst **不變**。worst 不變是這個改動誠實的地方,不是缺陷。

**D3 — fallback 靠 hook,不靠模型自律。**
`harness-context.py` 是 SessionStart + UserPromptSubmit hook,每回合執行、壓縮壓不掉它的輸出。global-rules §G / round 3 F2 已量測「靠 prompt 自律的規則實測失守」,所以重讀提示必須有機械錨。但 `refs_for_phase()` 現有語意是「conditional ref 每回合提醒是噪音」(有測試鎖住),不能改它 —— 改走新函式 `carryover_refs_for_phase()`,兩者互不干擾。

**D4 — carryover 清單由 manifest 產生,不手抄。**
`harness_lib.py` 註解已立下規矩(`_phase_refs` 內容「由 load-manifest.json 的 phase 欄產生,不手抄」)。因此在 manifest 的 `condition` 字串加固定前綴 `[carryover] `,hook 以前綴挑,單一資料源不破。

### 3.8 `hooks/harness_lib.py` — 新增 carryover 查詢

在 `refs_for_phase` 之後新增(不動 `_phase_refs` / `refs_for_phase` / `PHASE_GATES` 任何既有行為):

```python
CARRYOVER_MARK = "[carryover]"


def _display_ref(path: str) -> str:
    """`<superpowers>/skills/X/SKILL.md` → `superpowers:X`;其餘原樣(加 ~/.claude/ 由 caller 決定)。"""
    if path.startswith("<superpowers>/skills/"):
        return "superpowers:" + path.split("/")[2]
    return path


def carryover_refs_for_phase(phase: float, claude_dir: Path | None = None) -> list[str]:
    """該 phase 依賴、但由更早 phase 一次性載入的說明書(manifest condition 帶 [carryover])。

    與 refs_for_phase 刻意分開:那支的語意是「本 phase 要 Read 的 refs」且明文排除
    conditional(每回合提醒是噪音);這支的語意是「本 phase 用得到但可能不在本 session
    context 的東西」,跨 session resume / 壓縮後 hook 是唯一還在的錨,必須提醒。
    """
    root = claude_dir if claude_dir is not None else Path.home() / ".claude"
    try:
        data = json.loads((Path(root) / "harness" / "load-manifest.json").read_text(encoding="utf-8"))
        records = data["profiles"]["feat-L"]["files"]
    except (OSError, json.JSONDecodeError, UnicodeDecodeError, KeyError, TypeError):
        return []  # fail-open,與 _phase_refs 一致
    out: list[str] = []
    for rec in records:
        if not isinstance(rec, dict) or rec.get("scope") != "main":
            continue
        if not str(rec.get("condition") or "").startswith(CARRYOVER_MARK):
            continue
        try:
            if float(rec["phase"]) != phase:
                continue
        except (KeyError, TypeError, ValueError):
            continue
        shown = _display_ref(str(rec.get("path", "")))
        if shown and shown not in out:
            out.append(shown)
    return out
```

## 5. 這個改動可能打壞什麼

### 5.1 Phase 4 的快篩四條失憶(**最大風險,無法完全消除**)
Phase 1 到 Phase 4 之間夾著整個 TDD,是流程中最容易被壓縮的區段。若「重讀 gate」沒觸發,Phase 4 會少掉 review-protocol B 節的 (a)(b)(c)(d):誤報不經機械快篩直接進 receiving、效能類 claim 沒 runtime 證據就採信、ad-hoc reviewer 沒被告知「勿呼叫 ReportFindings」→ 結果整份丟失。
緩解:hook carryover 行(每回合注入,壓縮壓不掉)+ 重讀 gate 的兩題自答。
**殘留風險**:模型自答「我記得」而不重讀。global-rules §G / round 3 F2 已量測靠 prompt 自律會失守 —— 這條**必須誠實寫進 Known Risks,不得宣稱已解決**。若日後實測失守,升級方向是把 gate 變成硬 hook(Phase 4 首次 dispatch reviewer 前若本 session 無 Read 記錄則 deny),但那要 PreToolUse hook + session 級狀態,本輪不做。

### 5.2 S / M scope 的載入點漂移
Phase 1 對 S 是跳過、對 M 是 1 輪。措辭已用「第一個實際發生的 review 迴圈」處理,但 manifest 只有 `feat-L` profile,S/M 沒有帳、也沒有 hook carryover 對應(carryover 表是從 feat-L 產的)→ **S 級跑起來,Phase 4 不會收到 carryover 提示**。機械化需要新增 `feat-S` / `feat-M` profile,本輪 out of scope,列入 `docs/next-time.md`。

### 5.3 hook 每回合多注入一行(省的是一次性,付的是重複性)
Phase 2 / 4 期間每個 user turn 多約 110 bytes。Phase 4 常見 20-40 turn → 約 2.2-4.4 KB,淨值仍然大幅為正,但性質不同:省下的 20,444 是可快取的一次性載入,付出的是每回合重複注入。要記在帳上,不要當免費。

### 5.4 `refs_for_phase(4.0)` 變成空集合
phase 4 剩下的 `feat-phase4-fix.md` 本來就是 conditional,所以本改動後 harness-context 的第四行(refs)在 Phase 4 會消失。既有測試 `test_hook_omits_refs_line_when_phase_has_no_refs` 用的是 phase 5,不會抓到這個變化。未來讀 hook 輸出的人可能誤以為「Phase 4 沒東西要讀」—— carryover 行就是補這個,並要在 `harness_lib.py` 的 `carryover_refs_for_phase` docstring 寫明兩者的分工(§3.8 已含)。

### 5.5 歷史驗收紀錄的基準轉移
`docs/specs/harness-context-slimdown/sc-verification.md` 記著「SC-2:123,885 → 129,332(+4.4%,FAIL)」。**那是當時的實測,不准回頭改** —— 改了等於竄改已驗收紀錄。本次的新數字寫進本 spec 的驗證紀錄檔(`docs/specs/harness-review-load-once/verification.md`),並在該檔開頭一句說明基準關係。這是很容易被「順手更新一下舊數字」打壞的地方。

### 5.6 `protect-harness.py` 會攔
`~/.claude/hooks/**` 在守備範圍內,Edit / Write 會 `ask`(不是 deny)。本改動要動兩支 hook + 測試 → 會跳權限確認,屬預期行為。**非互動 session 跑不完**,必須在互動 session 執行。`~/.claude/harness/**` 與 `~/.claude/commands/**` 不在守備範圍,不會攔。

### 5.7 跨 command 誤傷(最容易被忽略的一面)
`review-protocol.md` 被 /feat /mod /bug /refactor /perf + branch-lifecycle 六處引用。§3.6 的措辭若寫成「已載入所以別讀」,`mod-M`(phase 3 + phase 5 各載一次 review-protocol,phase 5 載 receiving)讀到會誤判自己不該載入 → /mod Phase 3 的 change-spec review 少了協定。所以措辭固定為「**載入時機由呼叫方 command 決定**」並點名 /mod 現況維持不變。
順帶記錄:`mod-M` 有同型重複(review-protocol × 2 = 4,019 bytes),**本輪刻意不改**(scope 紀律 B),寫進 `docs/next-time.md`;要改的話等本輪的失憶風險在真實 session 上驗過一輪再說。

### 5.8 superpowers 升版
manifest 那筆無條件載入指向 `<superpowers>/skills/receiving-code-review/SKILL.md`(現 6.2.0)。升版若改名/搬路徑,`harness_load_estimate.py` 會 exit 非 0(manifest 列了不存在的檔),會被抓到 —— 這條安全。真正的風險是上游若加入「每次 review 前必須重新呼叫」的硬規則,本改動就與上游衝突,升 superpowers 時要重看此條。

### 5.9 `/auto` 自主模式
auto.md 只有一句「Review loop 內的 finding 處置照 receiving 紀律走,不需逐條問」,不涉及載入時機;`auto-wave.md` 全檔無 review / receiving 字樣 → **本改動與 /auto 無衝突**(已 grep 確認)。但 `goal_efficiency_mode` 的 wave batch 會壓縮 phase 邊界,Phase 2/4 可能落在同一 wave,carryover 行的觸發頻率是否合理未實測 —— 列為觀察項,不是 blocker。
